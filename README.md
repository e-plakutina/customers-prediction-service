# Прогноз числа гостей на 7 дней вперед

Модель прогнозирует число гостей точки на каждый из следующих 7 дней. Данные - открытый датасет
**Rossmann Store Sales**: магазины сети выступают аналогом ресторанов, число покупателей за день - аналогом числа гостей.

**Результат на отложенном периоде (6 недель, 20.06-31.07.2015):** LightGBM ошибается в среднем на **50 гостей в день
(MAPE 6.2%)**, обязательный наивный бейзлайн "тот же день неделю назад" - на 131 гостя (MAPE 16.8%).
Недельная сумма гостей точки прогнозируется с медианной ошибкой 2.9%.

## Данные

### Откуда и как воспроизвести

Исходный датасет - [Rossmann Store Sales](https://www.kaggle.com/datasets/pratyushakar/rossmann-store-sales)
(Kaggle): дневные данные 1115 магазинов за 01.01.2013-31.07.2015 (`train.csv`, 38 МБ), характеристики магазинов
(`store.csv`) и план работы на 01.08-17.09.2015 без числа покупателей (`test.csv`).

Соответствие задаче: `Store` - точка (ресторан), `Customers` - число гостей (целевая переменная), `Sales` - выручка,
`Sales / Customers` - средний чек. В коде оставлены исходные названия колонок Rossmann.

Сырые файлы не хранятся в репозитории. Их скачивает скрипт:

```bash
python make_dataset.py
```

Скрипт скачивает датасет через `kagglehub` (если не получилось - печатает инструкцию для ручного скачивания
в `data/raw/`), проверяет колонки и число строк и собирает `data/processed/` для магазинов выборки.
Обработанная выборка (1.3 МБ) лежит в репозитории, поэтому для обучения и прогноза скачивание не обязательно.

### Выборка из 40 магазинов

Детальный анализ и моделирование проводятся на выборке из 40 магазинов (36 024 дня). Выборка отобрана в ноутбуке
`01_data_research` по правилам, выведенным из данных всей сети: стратификация по сегменту (тип магазина) и росту спроса,
обязательное включение "проблемных" магазинов (пробел в выгрузке, ремонты, аномальные дни, открытие конкурента,
появление в данных позже), проверка, что выборка по ключевым характеристикам не хуже случайной. Цепочка
воспроизведения: ноутбук 01 → `data/processed/selected_stores.csv` → `make_dataset.py` → `data/processed/`.

### Выбор датасета

Были рассмотрены несколько вариантов датасета.
1) Датасеты из сферы ресторанов:
   1) [Recruit Restaurant Visitor Forecasting](https://www.kaggle.com/c/recruit-restaurant-visitor-forecasting)
   + в датасете представлены реальные данные
   + в датасете есть недельная сезонность, годовые тренды, праздничные всплески
   - довольно мало данных, чтобы корректно разделить их на трейновую и тестовую выборки
   - отсутствие данных по выручке или среднему чеку
   - в качестве тестовых данных выбран период, когда количество гостей становится выше нормы (тк период праздничный), нельзя оценить, как модель ведет себя в стандартные периоды
   - два разных источника данных - AirRegi и HPG: идентификаторы ресторанов в них разные. Далеко не все рестораны присутствуют в обеих системах одновременно (для связи используется специальная таблица маппинга store_id_relation.csv).
   2) [Restaurant Sales-Dirty Data for Cleaning Training](https://www.kaggle.com/datasets/ahmedmohamed2003/restaurant-sales-dirty-data-for-cleaning-training)
   + много данных
   - синтетический датасет, то есть нет реальной сезонной зависимости, из-за этого отсутствуют адекватные рыночные тренды, праздничные всплески и недельная сезонность
   - данные удалены хаотично, а не представляют реальные пропуски (ресторан закрыт)
   - пропуски - это сломанные ячейки внутри отдельных заказов
   - датасет - это лог покупок блюд, а не посещаемости
2) Датасеты из сферы ритейла:
   1) [Rossmann Store Sales](https://www.kaggle.com/datasets/pratyushakar/rossmann-store-sales)
   - датасет не про ресторанный бизнес, он про ритейл
   + реальные исторические данные
   + большой датасет (охватывает 31 месяц)
   + присутствует недельная сезонность, можно отследить годовые тренды, присутствуют флаги выходных дней
   + присутствуют периоды, когда магазины закрывались на ремонт, то есть можно проверить модель на обработку длительных пропусков

**Выбран Rossmann Store Sales.**

Требуется Python 3.11-3.12. Версии всех библиотек закреплены в `uv.lock` и `requirements.txt`, случайность засеяна
(`SEED = 42`), повторный запуск дает те же числа.

**С uv (рекомендуется):**

```bash

uv run --group data python make_dataset.py                 # данные (необязательно: выборка уже в репозитории)

uv run python predict.py --date 2015-08-01 --restaurant 75 # прогноз на 7 дней
```

### Прогноз: `predict.py`

```bash
python predict.py --date 2015-07-11 --restaurant 65 [--output forecast.csv]
```

- `--date` - первый день прогноза. Модель видит историю только до предыдущего дня, план работы на 7 дней
  (расписание, промоакции, праздники, каникулы) берется из данных.
- Если дата внутри истории (до 25.07.2015), кроме прогноза печатаются факт и метрики недели в сравнении
  с бейзлайном. Настоящий прогноз на будущее - `--date 2015-08-01`: история заканчивается 31.07.2015, план на август
  есть в `test.csv` для 30 магазинов выборки из 40.
- Некорректная дата, неизвестная точка, слишком короткая история, отсутствие плана, неверный формат входных данных
  или несовпадение модели с кодом - понятная ошибка и код выхода 2.

Модель не переобучается при каждом запуске: `predict.py` загружает `models/guest_forecaster.joblib`
и проверяет, что она обучена на том же наборе признаков, что и в коде.

### API (FastAPI)

```bash
uv run uvicorn customers_prediction.api:app --port 8000    # или: make api
```

Документация и форма для запросов - `http://localhost:8000/docs`. Модель и данные загружаются один раз при старте,
прогноз считает та же функция `forecast_week`, что и `predict.py`.

| метод | что делает |
|---|---|
| `POST /forecast` | прогноз на 7 дней: тело `{"restaurant": 75, "date": "2015-08-01"}` |
| `GET /restaurants` | точки: сегмент, до какой даты есть история и план |
| `GET /health` | статус сервиса и дата конца обучения модели |

```bash
curl -X POST http://localhost:8000/forecast -H "Content-Type: application/json" -d "{\"restaurant\": 700, \"date\": \"2015-06-01\"}"
```

Ответ - дни с прогнозом, планом (открыта ли точка, промоакция), бейзлайном `lag_7` и фактом, если он известен;
для прошедших недель - еще и метрики недели. Ошибки: неизвестная точка - 404, некорректный запрос, нет плана или
слишком короткая история - 422 с текстом причины.

## Принятые решения

**Коротко.** Пропуски разделены на три случая: регулярно закрытый день получает 0 гостей по правилу и не входит
в метрики, сбой выгрузки и период, когда точки нет (ремонт), - неизвестный спрос, пропуск, через который не
протягиваются лаги. Модель прогнозирует отклонение числа гостей от недавнего уровня точки в логарифме по лагам того же
дня недели, промоакциям и календарю праздников и событий, причем все признаки для дня t строятся только из данных
не позже t - 7 или из заранее известного плана - поэтому одна модель подходит для всех 7 дней горизонта и не может
заглянуть в будущее. Решения принимались на трех фолдах внутри трейна с расширяющимся окном (зима, весна, лето),
а отложенный период использован один раз, для финального сравнения. Основная метрика - MAPE, MAE приводится
в гостях.

### Пропуски и выбросы

- **Закрытый день** (серия закрытых дней короче 3) - 0 гостей по правилу, в прогнозе тоже 0, в метрики не входит.
- **Точки нет** (закрытие от 3 дней подряд: ремонт, магазин появился позже) и **сбой выгрузки** (у 9 магазинов нет
  второго полугодия 2014 года) - спрос неизвестен, значение - пропуск. Лаги не протягиваются через такие периоды,
  а признак `level_age` сообщает модели, что уровень точки устарел.
- **Аномалия** "открыт, но 0 гостей" оказалась последним днем длинного закрытия - пропуск.
- **Выбросы** найдены как отклонение от медианы таких же соседних дней (раздел 7 ноутбука 02). 78% из них - события
  календаря (Рождество, праздники, Пасха, карнавал, открытие после ремонта): это реальный спрос, его модель описывает
  признаками, новогодние дни не удалялись. Ограничение оставшихся выбросов при обучении проверено и не улучшило прогноз.

### Признаки

Генерация признаков - функция `build_features` (`src/customers_prediction/features.py`), одна и та же при обучении
и прогнозе:

- уровень точки (среднее за последние 24 открытых дня не позже t - 7) и целевая `log(гости) - уровень`;
- лаги того же дня недели 7-28 дней назад, их медиана, промоакция в дни лагов, значение год назад;
- план на день t: промоакция, день недели, месяц, день месяца, школьные каникулы;
- дни до и после праздника с типом праздника, дни относительно Пасхи, Рождества и карнавала;
- дни после открытия и до закрытия на ремонт;
- характеристики точки: сегмент, ассортимент, конкурент, номер точки.

Кандидаты (день месяца, каникулы, конкурент, номер точки и др.) принимались, только если улучшали MAPE
в среднем и хотя бы в двух фолдах из трех (раздел 7.1 ноутбука 03).

### Валидация

Разбиение только по времени. Трейн - до 19.06.2015, отложенный период - последние 6 недель (20.06-31.07.2015).
Внутри трейна - 3 фолда по 6 недель с расширяющимся окном: зимний (Рождество), весенний (Пасха, майские праздники),
летний (ближайший к отложенному периоду). Отложенный период проверяется как 6 последовательных недельных прогнозов.
Масштабирование и кодирование категорий настраиваются только на обучающих данных (`Pipeline`). Отсутствие утечки
проверено тестом: если стереть данные после даты прогноза, признаки 7 дней горизонта не меняются.

### Почему MAE и MAPE

- **MAE** - ошибка в гостях: понятна бизнесу и напрямую переводится в число сотрудников на смене и объем закупок.
  Но в ней доминируют крупные точки.
- **MAPE** - ошибка в процентах, где каждая точка весит одинаково. Точки различаются по потоку почти в 5 раз,
  и для сети важно, чтобы прогноз был хорош и для маленькой точки, а не только для крупных. Модель обучается на
  логарифме отношения к уровню точки, то есть минимизирует именно относительную ошибку, поэтому MAPE - основная
  метрика для выбора решений. Знаменатель не бывает близким к нулю: метрики считаются только по открытым дням,
  где гостей всегда больше 0.
- **WAPE** (сумма ошибок / сумма факта) - дополнительно: относительная ошибка, где точки весят пропорционально потоку.

Все три метрики дают одинаковый порядок моделей, то есть выводы не зависят от выбора метрики.

### Модели

- **Бейзлайны:** `lag_7` (тот же день неделю назад, обязательный), `lag_14` (две недели назад - та же фаза
  промоакции, которые чередуются по неделям), `median_7_28` (медиана того же дня 1-4 недели назад).
- **Ridge и LightGBM на одних и тех же признаках.** LightGBM точнее, особенно в рождественский период, где эффект дня
  зависит от сочетания признаков; в обычные дни линейной модели почти достаточно.
- **Итоговая модель:** LightGBM (63 листа, не меньше 200 дней в листе, 150 деревьев) - общая для всех точек и отдельная
  для сегмента `high_check`.
- **Альтернативный подход к сезонности - SARIMAX** (statsmodels): регрессия с ошибками ARIMA(1, 1, 1) для каждой точки,
  сезонность и события заданы регрессорами. Prophet не использовался: в нем нет авторегрессии, а для прогноза на неделю
  главное - текущий уровень точки, который SARIMAX обновляет по последним наблюдениям.

## Результаты

### Отложенный период (20.06-31.07.2015, 1470 открытых дней, 40 точек)

| модель | MAE, гостей | MAPE, % | WAPE, % |
|---|---|---|---|
| бейзлайн `lag_7` (тот же день неделю назад) | 131.4 | 16.8 | 16.0 |
| бейзлайн `lag_14` (тот же день две недели назад) | 70.1 | 8.7 | 8.6 |
| бейзлайн `median_7_28` | 81.6 | 10.5 | 10.0 |
| Ridge | 58.2 | 7.1 | 7.1 |
| SARIMAX | 55.9 | 6.9 | 6.8 |
| **LightGBM (итоговая модель)** | **50.4** | **6.2** | **6.2** |

LightGBM уменьшает ошибку `lag_7` на 62% (MAE) и 63% (MAPE), лучшего на этом периоде бейзлайна `lag_14` - на 28% и 29%.
Улучшение устойчиво: по бутстрепу блоков "точка x неделя" интервал улучшения MAPE относительно `lag_14` - 24.9-32.3%,
улучшение есть во всех 2000 выборках. LightGBM лучше `lag_7` и `median_7_28` у всех 40 точек и лучше всех бейзлайнов
во всех группах точек, включая проблемные.

### Фолды внутри трейна (средняя MAPE, %)

| модель | зима | весна | лето | среднее |
|---|---|---|---|---|
| `lag_7` | 23.7 | 19.1 | 14.9 | 19.2 |
| `median_7_28` | 21.3 | 11.8 | 10.6 | 14.6 |

| SARIMAX | 12.1 | 7.1 | 8.0 | 9.0 |

### Интерпретация

## Что это значит для бизнеса

В среднем точка принимает 819 гостей в день. На отложенном периоде:

| | LightGBM | бейзлайн `lag_7` |
|---|---|---|
| ошибка в день, медиана | 35 гостей | 101 гость |
| ошибка в день в 90% дней не больше | 112 гостей | 276 гостей |
| дней с ошибкой до 5% | 49% | 17% |
| дней с ошибкой больше 20% | 2% | 33% |
| ошибка недельной суммы гостей точки, медиана | 2.9% | 15.5% |

- **Смены.** В половине дней ошибка не больше 35 гостей (около 4% среднего потока), в 9 днях из 10 - не больше 112 гостей. Этого
  достаточно, чтобы планировать смены с небольшим запасом: ошибка больше 20% бывает в 2% дней, у бейзлайна - в каждый
  третий день.
- **Закупки.** Для закупок важна сумма за неделю: она прогнозируется с медианной ошибкой 2.9% (в 90% недель - не больше
  7.3%), систематического завышения или занижения нет (смещение -0.6%).
- **Ограничения.** В отложенном периоде нет праздников. В праздничные периоды ошибка выше: в рождественском фолде MAPE
  12.9%, поэтому на праздники прогноз стоит дополнять запасом или ручной корректировкой. Разовые провалы спроса
  (погода, местные события) модель не предсказывает.

## Что бы я доделала

- **Более свежие данные для ближних дней горизонта.** Сейчас все признаки берутся не позже t - 7; модель
  "дата прогноза x горизонт" могла бы использовать и последние дни. SARIMAX, который так делает, точнее в зимнем фолде.

- **Ridge с взаимодействиями признаков** (`Promo x segment`, `DayOfWeek x segment`, `DayOfWeek x Promo`) - проверить,
  какую часть отставания линейной модели можно закрыть ручными признаками.
- **Интервал прогноза**, а не одна точка: квантильная регрессия LightGBM или распределение ошибок на фолдах.
- **Внешние данные:** погода и местные события объяснили бы часть разовых провалов спроса (для обучения нужны
  исторические прогнозы погоды, а не факт).
